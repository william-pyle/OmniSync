Upgrade from 0.1.x

  1. Quit the old OmniSync app from its tray menu, then run the 0.2.0 installer. Do not uninstall or delete app data first.
  2. Open OmniSync from the Start menu. Your saved source selections, exclusion rules, device identity and preferences are retained.
  3. Choose destination in Overview or Settings. Browse to an existing folder or type an absolute path, including a network share. Review the impact and apply.
  4. All included source files are copied to the new destination. If you previously paused backup, choose Resume. Old Google Drive copies remain untouched; they are not downloaded or deleted.
  5. Version 0.1.x does not have an updater, so this first upgrade must be installed manually. The new version checks GitHub Releases automatically when it starts.

Choose any available folder

Use a folder on another disk, Google Drive for desktop, another cloud client, a mapped drive, or a UNC share using its UNC path. The folder must already exist and be writable by your Windows account. OmniSync creates an OmniSync subfolder inside it.

The destination must be separate from every selected source and from OmniSync app data. Links and junctions are rejected to avoid backup loops. Cloud destination placeholders are supported when Windows exposes normal read/write file operations.

For Google Drive, install and sign in to the real desktop client, then choose its mounted or mirrored location. OmniSync needs no Google API project or OAuth credentials. Backed up means the bytes were verified at the selected folder; check your cloud client for onward-upload status.

A destination identity marker prevents silently writing to a different disk mounted at the same drive letter. If a drive disconnects or the marker disappears, copying waits with an issue. Reconnect it, then use Sync now.

Backup files and retained versions

Inside OmniSync/<device-id>/files/, each source has a stable named folder with its original directory tree and ordinary filenames. Same-named sources are kept separate by their stable IDs.

OmniSync/<device-id>/versions/ contains immutable snapshots with SHA-256 verification. Recovery catalogs are under catalogs/. Independently edited destination files are preserved under conflicts/ after you explicitly acknowledge a conflict.

The current readable file and its version snapshot are separate copies. Allow at least twice the included data size for the initial backup, plus space for retained versions and temporary copies. Versions are not automatically pruned.

Every transfer uses a temporary file in the destination directory, flushes it, reads back its checksum and publishes it by rename. Interruptions keep source files and earlier verified copies intact. The local job queue is durable; an interrupted copy retries safely.

Changes flow from source to destination. Destination edits never replace source files. Excluding a file, removing a source, deleting a local source or changing destinations retains existing backups.

Sources, exclusions and restore

Source eligibility remains fixed local NTFS files and directories. Source links, junctions, offline placeholders and encrypted EFS files are excluded. The expanded drive support applies to the backup destination.

Keep using Folders, Rules and Explorer right-click actions. Exact files have priority over subtree rules, then folder patterns, then global patterns; later equally specific rules win. A destination change does not replace these settings.

Restore verifies a version and writes outside the source and backup folders. Existing destination files are preserved using a numbered restored filename. To recover an earlier destination, select it in Settings and use Restore > Find recovery catalogs.

The upgrade archives old Google item/job records in the local database and preserves previous configuration revisions. Old Google backups stay accessible in Google Drive. The new app does not use the Google API for backup, restore or cleanup. Do not run 0.1.x against the migrated database; the schema version prevents an unsafe downgrade.

Updates and installation

OmniSync checks the latest stable release in william-pyle/OmniSync on startup. Settings also has Check for updates. An unavailable network does not block local backups.

A newer release offers Download update. The native app accepts only the expected installer and checksum assets from the official repository over HTTPS, verifies size and SHA-256, and rechecks the downloaded executable before installation.

Close OmniSync & install is a separate explicit choice. Windows requests administrator confirmation. After approval, OmniSync finishes its current backup checkpoint and closes. Setup waits for it without killing the app or restarting Explorer. Open the new version from the Start menu after setup.

The installer is currently unsigned. Windows may display an unknown-publisher warning. SHA-256 detects a mismatched download; it is not an Authenticode publisher certificate.

Installing over an existing version preserves app data at %LOCALAPPDATA%\app.omnisync.desktop. Uninstall keeps sources, destination backups and per-user settings. Explorer may need a later sign-out to reload a shell DLL.

Build and publish

Use Windows 11 x64, Rust 1.98.1 with MSVC build tools, Node 24, WebView2 and NSIS 3. Run npm ci, then powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1. The script builds the frontend, runs Rust tests, builds production native binaries, smoke-tests the shell DLL and packages an installer plus SHA-256 checksum in out/.

The GitHub Actions workflow compiles and tests pushes to main and pull requests. Push a version tag such as v0.2.0 to build and publish a GitHub Release after the build, source audit and Edge interface tests pass. The release uses the GitHub-hosted build artifact.

Before tagging a later release, update Cargo.toml, Cargo.lock, package.json, package-lock.json, src-tauri/tauri.conf.json and the installer fallback version; add docs/releases/<version>.txt. Run node scripts/check-version.mjs. Already published releases are never overwritten by a workflow rerun.

The release job receives only the repository contents permission needed to publish assets. No personal token or Google secret is required. Local signing hooks remain available in scripts/build.ps1 for a publisher-owned certificate.
